Troubleshooting
Event count frozen · nothing new
#1 suspect: server disk full. The indexer locks indices read-only. Check the server first, always.
df -h / → sudo lvextend -l +100%FREE /dev/ubuntu-vg/ubuntu-lv → sudo resize2fs … → restart 3 services
No Suricata alerts appear
Check the chain in order: is eve.json being written → is the localfile block in ossec.conf → was the agent restarted after the edit?
sudo tail /var/log/suricata/eve.json · sudo grep -A2 suricata /var/ossec/etc/ossec.conf
Auth failures never appear (Kali)
Kali is journal-only — there is no /var/log/auth.log. The agent reads journald by default; don't add a second journald block.
journalctl -n 20 | grep -i sudo → confirm the events exist
One VM can't reach another
All lab VMs must be on UTM Shared Network. A bridged box sits on a different subnet and routes to the internet instead.
ping <SERVER_IP> → “Time to live exceeded” from a public IP = wrong network mode
Looking but see nothing
Wrong page, filter or window. Status lives on Endpoints; events on Threat Hunting → Events. A rule.level filter hides level-5 auth events.
Clear filters · time range = Last 24 hours · Refresh

WhyFIM is change-based, not signature-based. Wazuh has no idea a file is malicious — it only knows one appeared where none should. That is exactly why the enrichment step exists.
On the agent
1

Watch /root in real time

Add to the existing <syscheck> block, beside the other <directories> lines.

$ sudo nano /var/ossec/etc/ossec.conf <!-- inside <syscheck> --> <directories realtime="yes">/root</directories>
Tiprealtime="yes" uses inotify, so the event fires on the write instead of waiting for the next scan.
2

Install jq

The response script parses alert JSON with it. Verify it landed — this is the single most common cause of a silently broken pipeline.

$ sudo apt install jq -y $ which jq # /usr/bin/jq
EOLOn an end-of-life release the security pocket 404s, so apt update exits non-zero. Chaining apt update && apt install silently skips the install. Run the install on its own.
3

Write the response script

Hardened: it verifies its dependency, refuses paths outside the monitored directory, confirms the delete, and logs every outcome.

$ sudo nano /var/ossec/active-response/bin/remove-threat.sh #!/bin/bash LOG="/var/ossec/logs/active-responses.log" MONITORED_DIR="/root" IFS= read -r INPUT_JSON log() { echo "$(date '+%Y/%m/%d %H:%M:%S') remove-threat: $1" >> "$LOG"; } command -v jq >/dev/null 2>&1 || { log "FAIL jq not installed"; exit 1; } FILE=$(printf '%s' "$INPUT_JSON" | jq -r '.parameters.alert.data.virustotal.source.file // empty' 2>/dev/null) [ -n "$FILE" ] || { log "FAIL no file path in alert"; exit 1; } case "$FILE" in "$MONITORED_DIR"/*) ;; *) log "REFUSED path outside $MONITORED_DIR: $FILE"; exit 1 ;; esac if rm -f "$FILE" && [ ! -e "$FILE" ]; then log "OK deleted $FILE" else log "FAIL could not delete $FILE" exit 1 fi exit 0
Read itMost guides ship four lines that pipe alert JSON straight into rm -f as root, with no path check and an unconditional exit 0. That is arbitrary root deletion driven by input you do not control.
4

Permissions, then restart

Wrong ownership or a missing execute bit means the agent cannot invoke it.

$ sudo chmod 750 /var/ossec/active-response/bin/remove-threat.sh $ sudo chown root:wazuh /var/ossec/active-response/bin/remove-threat.sh $ sudo systemctl restart wazuh-agent # expect -rwxr-x--- root wazuh
On the manager
5

Custom FIM rules

Re-fire the built-ins at level 7, scoped to /root, so the integration can bind to privileged activity only.

$ sudo nano /var/ossec/etc/rules/local_rules.xml <group name="syscheck,"> <rule id="100200" level="7"> <if_sid>550</if_sid> <field name="file" type="pcre2">^/root(/|$)</field> <description>File modified in /root</description> </rule> <rule id="100201" level="7"> <if_sid>554</if_sid> <field name="file" type="pcre2">^/root(/|$)</field> <description>File added to /root</description> </rule> </group>
What550 = checksum changed. 554 = file added. You are relabelling them, not replacing them. The <field> line is what limits them to /root; drop it and every monitored directory, including the /etc and /usr/bin defaults, feeds the VirusTotal integration.
6

VirusTotal integration

Scope it to those two rule IDs. Not to all FIM activity.

$ sudo nano /var/ossec/etc/ossec.conf <integration> <name>virustotal</name> <api_key>PASTE_YOUR_VT_API_KEY</api_key> <rule_id>100200,100201</rule_id> <alert_format>json</alert_format> </integration>
QuotaFree tier is 4 lookups/min, 500/day. Widen this beyond privileged directories and routine churn will exhaust it, after which lookups fail quietly.
7

Command and active response

Two blocks in the same file, and the order is not optional.

<command> <name>remove-threat</name> <executable>remove-threat.sh</executable> <timeout_allowed>no</timeout_allowed> </command> <active-response> <command>remove-threat</command> <location>local</location> <rules_id>87105</rules_id> </active-response>
OrderEvery <command> must sit above every <active-response>. Get it wrong and the manager refuses to start.
TrapThe default config ships a commented <active-response> sample. Paste inside those <!-- --> markers and your block is inert while looking perfectly correct.
8

Restart and actually check

systemctl status can report active while the manager is not processing. Read the log.

$ sudo systemctl restart wazuh-manager $ sudo grep -n -B2 -A6 "remove-threat" /var/ossec/etc/ossec.conf $ sudo grep -iE "error|critical" /var/ossec/logs/ossec.log | tail -20
Test both directions
9

Positive test

Terminal one tails the log. Terminal two drops the file. EICAR is a standard test string, harmless by design.

# terminal 1 (agent) $ sudo tail -f /var/ossec/logs/active-responses.log # terminal 2 (agent) $ sudo curl -Lo /root/eicar.com https://secure.eicar.org/eicar.com $ sudo ls -la /root # expect: remove-threat: OK deleted /root/eicar.com
CorroborateIn the dashboard look for 100201 → 87105 → 553. Rule 553 is FIM independently observing the deletion, which beats the script reporting on itself.
10

Negative test

Prove the path validation is real, not decorative. Feed the script a disposable file outside the monitored directory.

$ sudo touch /tmp/canary $ echo '{"parameters":{"alert":{"data":{"virustotal":{"source":{"file":"/tmp/canary"}}}}}}' \ | sudo /var/ossec/active-response/bin/remove-threat.sh $ ls -l /tmp/canary $ sudo tail -n 2 /var/ossec/logs/active-responses.log # expect: canary survives # expect: REFUSED path outside /root: /tmp/canary
NeverDo not run this against an unhardened script, and never with a real path. Without the guard it deletes whatever you hand it, as root.
Troubleshooting
Alerts fire but the file is still there
#1 suspect: jq is missing. The script runs, extracts an empty string, rm -f "" does nothing, and it exits 0. Failure is indistinguishable from success upstream.
which jq  →  sudo apt install jq -y  →  retest
active-responses.log has only restart.sh lines
Wazuh does not write this log for you. Scripts log themselves. The bundled restart.sh does; most tutorial remove-threat.sh versions do not, on any path.
Add logging to the script — or verify removal with ls and rule 553 instead
Manager will not start after editing
A <command> block placed after an <active-response> block, or a block pasted inside the commented sample.
sudo grep -n -B2 -A6 "remove-threat" /var/ossec/etc/ossec.conf
Manager dispatches, nothing happens on the agent
Agent-side active response disabled, wrong ownership, missing execute bit, or whitespace before the shebang.
sudo grep -A3 "<active-response>" /var/ossec/etc/ossec.conf  ·  ls -l …/remove-threat.sh
Host log and dashboard timestamps disagree
Agent and manager on different timezones. Alerts carry UTC so SIEM correlation is fine, but local rendering differs — which is what breaks host-artifact-versus-SIEM timeline work.
timedatectl  →  sudo timedatectl set-timezone <manager zone>
Verdict changes between runs
Engine coverage moves. The same hash returned 65/67 one day and 64/67 the next. Consensus is a signal, not a fact.
Compare data.virustotal.positives against total in the alert document
What this does not prove
EICARA test string, not malware. You validated a pipeline, not a detection.
HashVirusTotal is a lookup. A file it has never seen returns clean. That is absence of evidence, not evidence of safety — novel payloads pass straight through.
SampleDeleting destroys the artifact you would need for IOC extraction. Quarantine is the better default on a server under investigation.
AccessThe payload is gone; the path that delivered it is not. Something wrote to /root as root and nothing here tells you how, or whether persistence was created.
